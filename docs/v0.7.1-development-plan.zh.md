# BraidPath 0.7.1 开发执行计划

从 `57d03589b6e4017568fd7d66ebdd7d73fe8d19fc` 开发。0.7.1 的主验收入口是统一客户端的一个 SOCKS5 监听。对同一个出口开启 `proxy-client --game-mode on` 后，一次 TCP CONNECT 下载和一次 UDP ASSOCIATE 必须共用聚合会话。批量下载走每路径已有的 H3 响应 STREAM，游戏走带本地期限、完整消息处理和有限副本的 DATAGRAM。每条入选路径使用一条数据 QUIC 连接。

交付顺序为 **接收可靠性 → 发送准入与观测 → 会话协议与产品入口 → 制品验收**。下列数字是本版工程门槛。所有阶段均待实施。开发分支为 `codex/v071-mixed`。

## 入口与协议范围

| 入口或流量 | 0.7.1 的行为 |
| --- | --- |
| 统一客户端，省略 Game 或显式 `--game-mode off` | 普通策略，批量 TCP 下载使用 native。普通 SOCKS5 UDP 沿用当前独立连接。 |
| 统一客户端，`--game-mode on` | 同出口的 SOCKS5 TCP 与 UDP 共用聚合会话。固定 TCP 映射也使用选定的下载策略。不同出口继续独立。 |
| 底层 `client`、`mesh-client` | 有 TCP 入口时，`--game-mode --native-return-stream` 选择同一混合策略。仅 UDP 的入口可选 Game。单独选择 native 需要 TCP 能力。独立策略用于各自支持的工作负载。 |
| TCP 上传、小记录、业务 ACK、RESET、探测 | 继续使用现有 DATAGRAM 通路。TCP 可靠范围、FIN、去重及故障恢复复用同一套业务 offset 状态。 |

两端同步升级。直接替换本次淘汰的策略头、互斥断言、调用方、测试和说明。0.7.0 仅以独立二进制参与性能对照，运行时没有旧协议解析、协商降级或兼容开关。BQ2C、业务 offset、H3 body 的记录格式继续承担各自现有职责。原生上传、额外 QUIC 连接、新 FEC、健康 STREAM 抢跑重传和预计完成时间选路均移出本版。

## 阶段一　保证接收压力解除后可靠数据能交付

**改动。** 从 [公共 TCP 接收](../src/runtime/tunnel/tcp.rs)、[native 读写](../src/runtime/tunnel/native_return.rs)和[接收预算](../src/runtime/tunnel/stream_budget.rs)入手。先让回归测试走真实的 `receive_native` 交接。当前重排槽位和业务字节申请失败都会直接返回，此时帧已由 H3 读出。

1. 为接收处理返回可区分的结果：已接纳、已处理重复、暂缺信用、流已关闭或协议错误。重复字节和携带 FIN 的记录分别处理。只对正式接纳的数据推进业务确认。
2. 让等待帧持有有界的暂存信用，在业务层接纳后转交或释放。明确每进程、每会话的字节与记录上限。沿用现有 32 MiB 进程暂存和每会话 64 槽的边界，将排队外仍由读任务或解码器持有的帧计入上界说明。上限耗尽时背压到对应 native reader。
3. 重试由信用释放、缺口推进或终止事件驱动。被拒的乱序帧不能占住填洞帧的最后一个位置；允许另一条路径提交前部缺口。处理 RESET、取消、FIN、会话关闭和旧代次回调，DATAGRAM 读取和其他流持续可服务。

**测试。** 分别耗尽字节信用和重排槽位。两个流争用预算，快路径先送后段，慢路径后送前段。至少一例只靠填洞与正常消费释放信用；至少一例由另一业务流释放共享信用。覆盖重复、零数据 FIN、等待中 RESET，以及 native 队列满时控制包与 UDP 到达。使用受控时钟或显式事件，无须等 WAN 偶发。

**通过门槛。** 健康连接上无需重连，完整输出 SHA256 一致，应用只见一次 FIN；待处理量始终在公布上限内，结束后暂存、业务信用和槽位回到初值。让原回归在基线暴露临时拒收造成的缺口，再验证修复。若实际入口已有其他恢复机制，保留证明，按真实失败点缩小改动。

## 阶段二　统一发送准入并限制提前写入量

**改动。** 在[方向发送循环](../src/runtime/tunnel.rs)、[额度与队列](../src/runtime/outbound.rs)、[Game 启动控制](../src/runtime/tunnel/game_startup.rs)和 [DATAGRAM writer](../src/runtime/tunnel/writer.rs)上完成。现有 native drain 可连续取出多条记录，先扣方向与组额度。将这次扣款替换为与实时流量共同仲裁的一次写入份额。

| 资源 | 仲裁及记账规则 |
| --- | --- |
| 方向和组的发送上限 | native 份额、DATAGRAM 原件、保护副本、业务重发和受此上限约束的控制包均进入同一方向及所属组账本。预留、提交、取消各有唯一结算点。分别公布唯一业务字节、估算的准入开销和传输层字节。Quinn 自动重传由传输层另计。 |
| 控制、实时和 bulk | 控制有前进机会。Game 原件和分片能使用实时预留，副本使用现有冗余预算。bulk 使用可用余量。预留计入方向与组上限。持续有竞争时，按确定的最大服务间隔验证 TCP 前进。 |
| 反馈 | Game 启动增长使用其 DATAGRAM 交付样本。native 的服务进度使用 writer 背压、待写字节和业务 ACK。列出 forward/reverse guard 的作用域，仅经验证的共享瓶颈信号可收紧整组。纯下载与稀疏 UDP 都要能用上可用带宽。 |
| native 写入 | 保留约 32 KiB 的业务记录及单一恢复所有者。每个 writer 同时只推进一条记录。每次仅授予一个能装入最小可用桶的字节份额，完成后重新仲裁。在代码和测试中固定每路径未结算份额数、队列字节上限及可提前交给 Quinn 的上限。 |

**半条记录的处理。** 首次写入前可取消并返还预留。一旦 H3 写入已开始，允许当前记录写完；若写入结果不明、承载失败或必须中止，终止该承载，按 retained offset 恢复。已部分写出的 body 不能接着写下一条记录。只有能证明尚未提交的额度才返还。保留每次提交时的路径及代次，延迟回调只结算原预留。

**观测与条件修复。** 用单调时钟记录入应用队列、进 writer、Quinn 接受、Quinn 选包装入以及对端完整交付；网络端到端时延用同一探测端的 echo RTT。按方向、承载、路径、代次汇总有界计数和直方图。选包装入和实际传输提交分别命名。核对 API 前过期、接受后本地逐出、关闭清理、已选包和待决数，未知原因单列。现有 [Quinn 入队 API](../vendor/quinn/src/connection.rs) 会在连接锁内检查期限，其[发送队列](../vendor/quinn-proto/src/connection/datagrams.rs)可逐出未发数据。结合 writer 与传输提交时间定位等待。

若已复现的混合场景超出实时门槛，且时间戳显示超线包在 Quinn 接受时尚未过期、主要等待发生在选包前，再把原始期限与代次带到出队处，增加有界的本地丢弃回执。同一事件只结算一次。若未触发该条件，保留原本到 Quinn 准入为止的 10 ms 语义。任何路径均遵守 QUIC 拥塞控制。

**测试与通过门槛。**

- 用假时钟覆盖最小合法速率、小组额度、一个 32 KiB 记录。逐次验证方向及组的累计提交不超过“初始可用突发额度＋期间补充额度”，取消后挂账归零。固定份额上限后验证 writer 满、换代次和首段成功后失败。
- 分别注入零 UDP、稀疏 UDP、持续 UDP、超预算 UDP；覆盖游戏原件、分片与副本、普通 TCP 上传和业务 ACK。健康的 30/30 Mbps 受控模型中，实时输入为每秒 50 条时，预热后每连续 1 秒两方向均须有新的可靠业务字节交付。超载时资源有界，压力移除后继续推进。
- 强制 cwnd 无空间和 STREAM 恢复积压，再恢复发送。到期原件和副本不得越过所声明的期限检查点，本地逐出不得计为网络判丢。故障测试中，注入事件的计数、归属和终态逐项核对；测不清的路径先补观测。

## 阶段三　替换策略协商并接入统一客户端

**改动。** 在 [CLI](../src/runtime/cli.rs)、[统一客户端策略构造](../src/runtime/proxy/client.rs)、[SOCKS5 命令路由](../src/runtime/proxy/socks.rs)和[聚合握手](../src/runtime/tunnel.rs)落地。基线同时有 CLI 的参数互斥及 `Policy::validate` 的运行时互斥；服务端解析请求后也执行该校验。

1. 将聚合握手中旧的 Game、native 两个可选头替换为一项必填、带版本的策略字段，字段名定为 `braidpath-policy`，取值分别为 `1/datagram`、`1/native`、`1/game`、`1/mixed`，对应普通 DATAGRAM、普通 native、Game DATAGRAM 和混合策略。两端共用编码与校验。首次握手、加路、重连都精确回显并校验，缺失、重复、未知值或与会话不一致的请求在登记路径前失败，客户端确认后才启用路径。
2. 统一客户端 `on` 直接构造混合策略，SOCKS5 UDP 复用同出口 TCP 的聚合连接器。两类入口共享 Game 的有效参数和消息大小校验，消除现有构造函数间可能造成的无意差异。同步更新帮助、运行文档、旧头和旧互斥测试。只删除本次替换的实现。
3. 统一客户端按真实默认速率参加产品验收。固定上、下行额度的对照由底层入口完成，服务端上限与代理宿主的共享预算各自继续生效。

**测试。** 两个新端点完成四种策略往返。注入缺字段、重复值、不支持版本、错回显及重连时策略不一致。对同一出口建立 SOCKS5 CONNECT 和 UDP ASSOCIATE，并发发送下载、上传、短请求和交替的单片/多片 UDP。另测半关闭、单路径断开、同一流在剩余路径上完成，以及恢复路径重新承载有效 native 数据。覆盖固定 TCP 映射与多出口隔离。

**通过门槛。** 一份会话快照同时显示同一 session ID 上的 native 回程业务字节和 Game DATAGRAM 原件，按路径核对连接标识。另在受控可保护场景观察到预算内副本。每条路径只有一条该会话的数据连接，UDP 消息边界、内容和去重正确，旧代次不能覆盖新代次状态。普通模式 smoke 通过。源码检索确认退役策略头的运行时读写及互斥分支均已删除。

## 阶段四　冻结负载并验收制品

**基准入口。** 扩展 [bench/tcp_lab.py](../bench/tcp_lab.py) 并复用 [link_lab](../examples/link_lab.rs) 的扰动。支持底层固定入口和真正启动 `proxy-client` 的 SOCKS5 入口。现有 `--entrance socks5` 本身不能证明启动了统一客户端。公共工具包含工作负载、评价器和方法。具体路径、端点、密钥、UTC 窗口、失败、重试和结论仅写入忽略目录 `local/v0.7.1/`。公共基准直接调用仓库模块。阶段二先实现固定时窗的生成器、计数器和评价器夹具，阶段三接入统一客户端，阶段四冻结同一套工具。为评价器加入四个小样本：基线 p99 无限、候选下载超时、分片缺一片、生成器提前耗尽上限。四种情形均须产生下文规定的判定。

**负载。** 三组负载分别计分。所有可靠传输按应用实际收到的唯一字节计算，并验证完整内容。

| 负载 | 执行方法 |
| --- | --- |
| 有限下载 | 空闲后单 TCP 下载 512 MiB，校验 SHA256，记录首字节及总耗时。 |
| 有限双向任务 | 同时启动 64 MiB 下载、32 MiB 上传、50 条/秒 UDP 和 1 KiB 短请求；完成后空闲 3 秒，再上传 4 MiB。分别统计双向重叠期与完整任务期。 |
| 持续竞争 | 同步启动双向饱和 TCP 与 50 条/秒 UDP，固定 30 秒，共 1,500 条 UDP echo，交替 128 和 1,200 字节应用载荷，每秒另发一次 1 KiB 短请求。停止生成后限时排空和校验。每方向预登记最大生成字节数，至少为该方向预期最高速率 × 30 秒 ÷ 8 的 1.25 倍。超出可用实验预算时，在开跑前缩减整个方案。 |

开跑前用 `字节数 × 8 / 方向可用上限` 算理论最低耗时，组上限和预设瓶颈取更紧者。将有限任务期限、收据期限、排空时间、字节总上限写入计划。默认有限任务期限取理论下界的 2 倍加 15 秒，固定窗排空 10 秒；更慢的模型在冻结前单列。夹具的收据计时起点必须明确。生成器提前耗尽字节上限或未能按期发包标记为无效夹具；候选因阻塞、丢弃、超时或校验错误按候选失败记录。

**基线与场景。** 三臂均使用相同端点、路径、拥塞控制、负载、构建目标和工具链。固定臂 A 用 `57d0358` 的 native，B 用同提交 Game，C 用 0.7.1 混合。固定上限先测上行 90／下行 30 Mbps，再测 30／30 Mbps。每组上限和冗余额度一致，记录各臂实际使用量。各臂的两端始终使用各自同一版本。产品组用同提交的统一客户端 off、on 分别作 A、B，C 用候选 on；三臂均采用产品默认速率。产品 A 的普通 UDP 有独立连接，其混合吞吐只作诊断。以固定组做同预算的混合吞吐归因。单独报告最强单路、各路径分配及共享瓶颈，区分独立资源和共同出口。

**先跑受控模型。** 覆盖对称健康路径、异构路径及共享瓶颈。将路径分组和故障时间写入预登记计划。健康模型的路径（RTT ms／单路 Mbps）依次取 40／50＋40／50、40／60＋100／20、40／50＋40／50 且共享上行 30 Mbps。使用 128 包队列、零注入丢失和种子 20261118。三臂保持同一模型。另用单路径断开/恢复、ACK 静默/恢复和 50% 随机丢失做降级测试。降级项验证有界、故障隔离和恢复后的完整性，单列耗时，不参与健康窗口的时延门槛。

**发布性能门槛。** 下表为健康参考场景的预设值。适用的每个区组分别判定，禁止跨场景取平均抵消失败。

| 指标 | 通过条件 |
| --- | --- |
| 可靠数据 | 所有任务按期完成、SHA256 一致；半关闭、消息边界、资源归还正确。单项失败即失败。 |
| 下载与上传 | 无实时流量的下载 C/A ≥95%。持续竞争中，固定组的下载、上传各自 C/A ≥90%；统一客户端默认组的下载、上传各自 C/B ≥90%。有限双向任务的上传 C/B ≥90%，空闲后 4 MiB 上传耗时 C/B ≤1.10。 |
| 完整 UDP | 按预定消息 ID 计数，缺失记为无限 RTT，重复只计一次且应用层重复交付为零。C 的全体 p99 ≤ B＋10 ms，完整缺失率 ≤ B＋0.5 个百分点。同时，至少 99% 的原定消息须在 200 ms echo RTT 内完整且正确返回。200 ms 是本版健康参考场景的工程值。 |
| 小请求与资源 | 固定组的短请求 p95 ≤ A 的 1.15 倍，产品组 ≤ B 的 1.15 倍。记录 CPU 秒/GiB、峰值 RSS、队列高水位、重复字节、两方向业务进度与传输开销。任何结构超过阶段一、二声明的硬上限即失败。 |

若 B 的有效消息样本产生无限 p99，相对 p99 记为不可比较，改用预设的 200 ms 绝对按时率和相对缺失率共同裁决。若 B 的夹具无有效样本，整个比较为证据不足。p95、p99 取排序后的第 ⌈p×N⌉ 项。计时口径统一为应用 echo RTT；10 ms 仅用于发送端本地准入。固定窗使用预定 1,500 条作为分母，分别公布按时、迟到、缺失与重复数。有效窗口中，候选未完成直接失败；基线无有效分母或线路资格不足则保留原始结果，判证据不足。

**一次有界 WAN 确认。** 本地各项通过后，冻结候选二进制 SHA256、拓扑、空载参考 RTT、方向和组上限、总字节/时长预算及下列次序。WAN 只执行 30 秒持续竞争，有限任务和故障压力在受控验收完成。固定组采用 30/30 Mbps，次序为 ABC、BCA、CAB；统一客户端默认组采用 CBA、BAC、ACB。共六个区组、18 个窗口，每个配置在各自组内各占一次首、中、末位。窗口名用 `window_a` 至 `window_r`，时间戳用 UTC。

每组开始前，以独立空载探测确认最快路径的中位 RTT ≤150 ms，核对同一批端点、路径数与分组；三臂逐路空载最小 RTT 的最大差 ≤10 ms。开测后的排队和丢失是结果，不能据此剔除候选。保留每个窗口的 1,500 条计划发送记录、双向进度和实际重叠时间；负载生成器须保持双向需求覆盖整个 30 秒。固定组与默认组分别判定：任一有效区组违反硬门槛即失败，全部适用门槛通过才可发布；未失败但因基准或资格不足无法完成判定，结论为证据不足。保留失败结果，不追加择优窗口。若要继续，需先修复具体机制或夹具，登记新的候选与计划。

**制品签收。** 候选在构建前更新 Cargo 版本与锁文件、CLI 帮助、运行说明和升级说明。按[现行 CI](../.github/workflows/ci.yml)通过 8 项检查，按[制品矩阵](../scripts/release-targets.json)生成 11 个目标制品并核对 SHA256、版本输出和可运行平台的 smoke。受控与 WAN 验收使用同一候选提交的固定制品，记录各平台哈希。把单元测试、真实 SOCKS5、受控性能、WAN、跨平台构建分别签收。发布标签与部署属于后续发布动作。

## 测试入口与交接

在开发工作树根目录执行。前四行是已有的定向入口。新增阶段回归分别归入对应模块或测试文件，并用具体测试名执行一次，确认运行数量大于零。最后三行用于候选冻结时的本地检查，其余矩阵交由 CI。

```sh
cargo +stable test --locked --lib native_return
cargo +stable test --locked --lib game_tests
cargo +stable test --locked --test tcp native_return_keeps_upload_half_close_udp_and_survives_one_path_closing
cargo +stable test --locked --test tcp game_mode_preserves_socks_udp_boundaries_fragmentation_and_tcp
python3 -m unittest discover -s bench -p 'test_*.py'
cargo +stable fmt --all -- --check
cargo +stable clippy --all-targets --locked -- -D warnings
```

每阶段交接记录列出源提交、改动入口、实际执行的测试、失败与修复、剩余未验证项。阶段四同时交付冻结的计划、逐窗原始记录、评价器输出与制品校验清单。任何正确性硬门槛失败均留在当前阶段修复。实时性或吞吐门槛失败时，优先依据等待阶段、额度和路径明细定位；预计完成时间选路留到后续独立提案。
